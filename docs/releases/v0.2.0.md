Release 0.2.0: removal became a move, so it can be undone

A deleted conversation now goes into a trash beside the sessions root. The rename
stays on one volume, so it is atomic — nothing is copied, and nothing is destroyed
at that point. Each entry records its workspace, title, size and when it was moved,
and stays restorable for a retention window: seven days by default, configurable per
profile with `config: { retentionDays: n }` on this plugin's row.

Three new routes do the rest. `POST /api/session.trash` lists what is in there,
purging anything past its window before it answers — so what the list shows is
exactly what can still come back. `POST /api/session.restore` puts one back where it
came from, refusing rather than overwriting when that name is taken. And
`POST /api/session.purge` destroys one entry or empties the whole trash.

In the sidebar foot, "Trash" sits beside the cleanup action, listing each entry by
title with its size and remaining days, offering Restore and Delete for good (which
asks first). The delete confirmation no longer promises permanence: it says what
actually happens, and its button reads "Move to trash".

Two things came out of building it. A purge with no record behind it used to report
success, because `rm` with `force` succeeds on a missing path — it is a 404 now. And
the client bundle is assembled into one flat factory scope, so the two dialogs
declaring the same top-level helper was a build error; the shared one moved into its
own module.

Suites: 30 package tests, 87 host-route checks against the built bytes (moving,
listing, restoring, a taken name refused, purging, expiry, a configured window,
emptying), 64 render and interaction checks.

**Install**

```sh
dsh plugin --profile <profile> add https://github.com/SereinHK/dsh-plugin-session-delete.git
```
